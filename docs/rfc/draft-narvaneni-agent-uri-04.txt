           The agent URI Scheme and Verifiable Agent Identity
                      draft-narvaneni-agent-uri-04

Abstract

   Software agents increasingly act on the Internet on behalf of people
   and organizations: they call APIs, browse websites, and delegate work
   to other agents.  Protocols such as A2A and MCP define how agents
   communicate, but there is no interoperable way to answer a prior
   question: _which agent is this, who operates it, and how can its
   claims be verified?_

   This document defines the agent URI scheme as a stable, human-
   readable identifier for an agent, a deterministic mapping from that
   identifier to an HTTPS-hosted Agent Identity Document, and a small
   set of mechanisms built on existing standards that let an agent prove
   its identity: signed statements binding the agent to its protocol
   metadata, an HTTP Message Signatures profile for requests made by the
   agent, short-lived credentials for ephemeral agent instances, and
   bindings to OAuth 2.0.  It deliberately does not define how agents
   communicate, describe their capabilities, or are invoked.

1.  Introduction

   Agents are now first-class actors on the Internet.  A single user
   task can cause an agent to call dozens of APIs and other agents, each
   of which needs to decide whether to serve the request.  Today those
   services can see a TLS client, an IP address, perhaps an OAuth access
   token issued to _some_ client, and a User-Agent string that anyone
   can forge.  They cannot reliably tell which agent is calling, who is
   accountable for it, or whether the protocol metadata it advertises
   was really published by its operator.

   Communication protocols already exist.  [A2A] defines agent-to-agent
   interaction and an Agent Card; [MCP] defines how agents reach tools
   and publishes server metadata; OpenAPI describes HTTP APIs.  Each of
   these describes _how to talk to_ an endpoint.  None of them defines a
   portable answer to _who_ an agent is that works across all of them.

   This document defines that missing identity layer:

   1.  *A name.* The agent URI (e.g., agent://example.com/planner) is a
       stable, human-readable identifier for an agent (Section 4).







Narvaneni & Ravi          Expires 23 April 2027                 [Page 3]

Internet-Draft                  agent-uri                   October 2026


   2.  *A document.* Every agent URI maps deterministically to an HTTPS
       URL that serves an Agent Identity Document listing the agent's
       operator, public keys, and links to its protocol metadata
       (Section 5).

   3.  *An anchor.* The document is trusted because of where it is
       served (the origin of the agent URI) or, for agents that need
       identity to survive a change of domain, because of a
       Decentralized Identifier (Section 6).

   4.  *Proofs.* Agents prove their identity by signing statements about
       their metadata (Section 7) and by signing the HTTP requests they
       make (Section 8), including from short-lived instances
       (Section 8.2).  Identity is connected to OAuth 2.0 authorization
       without new token formats (Section 9).

1.1.  Design Principles

   *  *Identify, do not invoke.* An agent URI names an agent.  It is not
      a locator for an endpoint and carries no invocation parameters.

   *  *Reuse before invent.* Every mechanism is a profile of an existing
      standard: HTTPS and well-known URIs [RFC8615], JWK [RFC7517], JWS
      [RFC7515], HTTP Message Signatures [RFC9421], OAuth 2.0, and DIDs
      [DID-CORE].

   *  *Anchor trust outside the document being verified.* A key is
      trusted because of the origin or DID it is published under, never
      because a document names it about itself.

   *  *Separate the name from the long-lived identity when needed.*
      Domains change hands; agents get renamed and sold.  The scheme
      supports a stable cryptographic identifier behind the human-
      readable name.

   *  *Work for agents that live for seconds.* Most agent executions are
      ephemeral.  Instances act under the identity of their agent
      without being individually published.

1.2.  Non-Goals

   The following are explicitly out of scope:

   *  Communication semantics, message formats, task lifecycles, and
      invocation.  These belong to A2A, MCP, OpenAPI-described APIs, and
      similar protocols.





Narvaneni & Ravi          Expires 23 April 2027                 [Page 4]

Internet-Draft                  agent-uri                   October 2026


   *  Capability, skill, or tool description.  Protocol metadata
      documents (for example, an A2A Agent Card or an MCP server card)
      remain authoritative for these.

   *  Transport bindings.

   *  Search, ranking, or registry services.  This document makes
      identity verifiable so that any registry can index agents without
      being trusted.

   *  Reputation, pricing, payments, and service levels.

   *  Authorization policy.  Knowing who an agent is does not grant it
      anything.

   Agent:  A software system that acts autonomously or semi-
      autonomously, typically on behalf of a person or organization.

   Operator:  The person or organization accountable for an agent.

   Agent URI:  An agent URI as defined in Section 4.  The human-readable

      statements, request signatures, and instance credentials made by
      the agent.

   Instance:  A running, typically short-lived execution of an agent
      that holds its own key pair and acts under the agent's identity
      (Section 8.2).

                                  |
             +--------------------+---------------------+
             |                    |                     |
        operator             keys (JWK Set)        links (rel, href)
                                  |                     |
        origin-anchored: trusted via HTTPS        A2A Agent Card,
        DID-anchored: keys from DID document      MCP server card,
                                                  OAuth client metadata

              Figure 1: From agent URI to verifiable identity

   A typical verification, for a request received by an API:

   1.  The request carries an HTTP message signature and a Signature-
       Agent field naming agent://example.com/planner.

   2.  The verifier maps the agent URI to its AID URL and retrieves the
       AID (or uses a cached copy).

   3.  The verifier finds the key identified by the signature, checks it
       is anchored (Section 6), and verifies the signature.

   4.  The verifier now knows which agent made the request and which
       operator is accountable.  Whether to serve it remains a policy
       decision.

4.  The agent URI Scheme

4.1.  Syntax

   The following ABNF [RFC5234] uses port and fragment from [RFC3986]
   and ALPHA and DIGIT from [RFC5234].









Narvaneni & Ravi          Expires 23 April 2027                 [Page 6]

Internet-Draft                  agent-uri                   October 2026


   agent-uri    = "agent://" agent-host [ name-path ] [ "#" fragment ]

   agent-host   = dns-name [ ":" port ]
   dns-name     = label *( "." label )
   label        = let-dig [ *61( let-dig / "-" ) let-dig ]
   let-dig      = ALPHA / DIGIT

   name-path    = 1*8( "/" name-segment )
   name-segment = lc-let-dig [ *61( lc-let-dig / "-" ) lc-let-dig ]
   lc-let-dig   = %x61-7A / DIGIT        ; a-z, 0-9

                      Figure 2: ABNF for the agent URI

   Additional constraints:

   *  dns-name MUST be a fully qualified domain name.  Internationalized
      domain names MUST be represented as A-labels [RFC5890] [RFC5891].
      IP literals and userinfo are not permitted.

   *  An agent URI MUST NOT contain a query component.

   *  An agent URI with an empty name-path (e.g.,
      agent://planner.example.com) identifies the domain's root agent.

   Examples:

   *  agent://example.com/planner

   *  agent://planner.example.com

   *  agent://example.com/acme/billing-assistant

   *  agent://example.com/planner#k1 (a reference to key k1 of the
      agent; see Section 4.4)

4.2.  Normalization and Comparison

   The canonical form of an agent URI is produced by:

   1.  Lowercasing the scheme and dns-name.

   2.  Converting any U-labels to A-labels.

   3.  Removing a port equal to 443.

   4.  Removing a single trailing "/" if present.





Narvaneni & Ravi          Expires 23 April 2027                 [Page 7]

Internet-Draft                  agent-uri                   October 2026


   Parsers MAY accept input that differs from the ABNF only by the
   deviations corrected above, and MUST normalize it.  Any other
   deviation (uppercase in name-path, percent-encoding, dot-segments, a
   query) MUST be rejected.

   Two agent URIs identify the same agent if and only if their canonical
   forms, with any fragment removed, are identical octet strings.  In
   particular, agent://example.com/planner and
   agent://planner.example.com are different agents, even if the same
   operator runs both.

   Agent URIs in AIDs, statements, signatures, and tokens MUST be in
   canonical form.

4.3.  Dereferencing

   An agent URI is dereferenced by mapping it to the HTTPS URL of its
   AID:

   https://<agent-host>/.well-known/agent<name-path>      (named agent)
   https://<agent-host>/.well-known/agent/_                (root agent)

   For example:

   +=============================+====================================+
   | Agent URI                   | AID URL                            |
   +=============================+====================================+
   | agent://example.com/planner | https://example.com/.well-         |
   |                             | known/agent/planner                |
   +-----------------------------+------------------------------------+
   | agent://example.com/acme/   | https://example.com/.well-         |
   | billing-assistant           | known/agent/acme/billing-assistant |
   +-----------------------------+------------------------------------+
   | agent://planner.example.com | https://planner.example.com/.well- |
   |                             | known/agent/_                      |
   +-----------------------------+------------------------------------+
   | agent://example.com:8443/   | https://example.com:8443/.well-    |
   | planner                     | known/agent/planner                |
   +-----------------------------+------------------------------------+

                  Table 1: Agent URI to AID URL mapping

   The root agent uses the reserved segment _, which cannot appear in a
   name-segment.  This allows the root AID and named AIDs to coexist on
   static file hosting.

   The mapping is purely syntactic.  No registry or index needs to be
   fetched to dereference an agent URI.

4.4.  Fragments

   A fragment in an agent URI identifies an Agent Key by its kid
   (Section 5.2).  For example, agent://example.com/planner#k1 refers to
   the key with "kid": "k1" in the agent's key set.  No other fragment
   semantics are defined.

5.  Agent Identity Document

5.1.  Format

   An AID is a JSON object [RFC8259] served with media type application/
   agent-id+json (Section 14.3).  It has the following members:

   id:  REQUIRED.  String.  The canonical agent URI that this document
      describes.

   operator:  REQUIRED.  Object identifying who is accountable for the
      agent, with members name (REQUIRED, string) and url (OPTIONAL,
      string, HTTPS URL).

   keys:  REQUIRED for origin-anchored agents; MUST be absent for DID-
      anchored agents.  A JWK Set [RFC7517] containing the agent's
      public keys (Section 5.2).

   did:  OPTIONAL.  String.  A DID [DID-CORE] whose DID document is the
      anchor for this agent's keys (Section 6.2).

   name:  OPTIONAL.  String.  A display name for people.  It has no
      identity semantics.

   status:  OPTIONAL.  String.  One of "active" (default), "suspended",
      or "retired" (Section 6.3).

   links:  OPTIONAL.  Array of link objects (Section 5.3).

   updated:  OPTIONAL.  String.  The time the document was last changed,
      as an RFC 3339 timestamp.

   Members not defined here MUST be ignored by verifiers that do not
   understand them.  Extension member names SHOULD be namespaced (e.g.,
   "acme_tier") to avoid collision with future versions of this
   document.

   An AID MUST NOT exceed 64 KiB.






Narvaneni & Ravi          Expires 23 April 2027                 [Page 9]

Internet-Draft                  agent-uri                   October 2026


5.2.  Keys

   Each key in keys MUST:

   *  contain only public key parameters;

   *  have a kid, which SHOULD be the JWK Thumbprint [RFC7638] of the
      key;

   *  have an alg member; and

   *  be usable for signatures ("use": "sig" or a key_ops containing
      "verify").

   Implementations MUST support EdDSA (Ed25519) and ES256.  Algorithms
   MUST be restricted as described in [RFC8725]; in particular, none and
   symmetric algorithms MUST NOT be accepted.

5.3.  Links

   Each link object has the following members, with the semantics of Web
   Linking [RFC8288]:

   rel:  REQUIRED.  String.  A registered link relation type or a URI.

   href:  REQUIRED.  String.  An absolute HTTPS URL.

   type:  OPTIONAL.  String.  The media type of the target.

   statement:  OPTIONAL.  String.  An Agent Statement (Section 7) about
      the target.

   Link relations expected to be common include:

       +=======================+===================================+
       | Relation              | Target                            |
       +=======================+===================================+
       | agent-card            | The agent's [A2A] Agent Card      |
       +-----------------------+-----------------------------------+
       | mcp-server-card       | The agent's [MCP] server metadata |
       +-----------------------+-----------------------------------+
       | service-desc          | An OpenAPI or other API           |
       |                       | description [RFC9727]             |
       +-----------------------+-----------------------------------+

   A link to a target on the *same origin* as the agent URI is trusted
   to the same degree as the AID itself.  A link to a target on *any
   other origin* MUST carry a statement; verifiers MUST ignore cross-
   origin links without a valid statement.

5.5.  Retrieval and Validation

   To obtain the AID for an agent URI, a verifier:

   1.  Parses and canonicalizes the agent URI (Section 4.2), rejecting
       it on failure.

   2.  Constructs the AID URL (Section 4.3).



Narvaneni & Ravi          Expires 23 April 2027                [Page 12]

Internet-Draft                  agent-uri                   October 2026


   3.  Applies the request-destination restrictions of Section 12.3.

   4.  Sends an HTTPS GET with Accept: application/agent-id+json,
       validating the server certificate for dns-name.

   5.  Follows redirects only to URLs with the same origin as the AID
       URL.

   6.  Rejects responses larger than 64 KiB, or that are not valid JSON
       objects.  Verifiers MUST NOT reject a response solely because its
       media type is application/json (to support static hosting) but
       MUST reject any other media type.

   7.  Rejects the document unless its id member is identical to the
       canonical agent URI.

   8.  If did is present, performs the DID binding check of Section 6.2.

   Verifiers SHOULD cache AIDs according to HTTP caching [RFC9111].
   Operators SHOULD NOT set a freshness lifetime longer than 24 hours,
   so that key removal takes effect promptly (Section 6.3).  Verifiers
   SHOULD cache failures for a short period to limit repeated fetches.

6.  Anchoring

   An Agent Key is _anchored_ when the verifier has established that the
   agent's controller published it.  This document defines two anchoring
   modes.  An agent uses exactly one.

6.1.  Origin-Anchored Agents

   The AID contains keys and no did.  The keys are anchored by the HTTPS
   retrieval of Section 5.5: control of the agent URI's origin is
   control of the agent's identity.

   This mode needs nothing beyond a web server.  Its weakness is that
   identity is exactly as durable as control of the domain: if the
   domain lapses or is transferred, so does the agent's identity
   (Section 12.2).

6.2.  DID-Anchored Agents

   The AID contains a did member and no keys.  The agent's keys are the
   verification methods in the DID document's assertionMethod and
   authentication relationships [DID-CORE].

   The binding between the agent URI and the DID MUST be bidirectional:




Narvaneni & Ravi          Expires 23 April 2027                [Page 13]

Internet-Draft                  agent-uri                   October 2026


   *  the AID retrieved for the agent URI names the DID in did; and

   *  the DID document lists the canonical agent URI in its alsoKnownAs
      property.

   Verifiers MUST check both directions and MUST treat the agent as
   unverified if either is missing.

   DID-anchored agents can change their human-readable name without
   changing their identity: the operator publishes an AID under the new
   agent URI and adds the new URI to alsoKnownAs.  Verifiers that record
   the DID (rather than only the agent URI) keep continuity across the
   rename.

   DID methods that support verifiable key rotation history (for
   example, [DID-WEBVH]) are RECOMMENDED.  Verifiers MUST maintain an
   allowlist of DID methods they support and MUST reject any other
   method.

6.3.  Lifecycle, Rotation, and Revocation

   *  *Rotation.* Operators add the new key, start using it, and remove
      the old key once signatures made with it are no longer expected to
      be verified.

   *  *Revocation.* Removing a key from the AID (or DID document)
      revokes it.  Verifiers learn of revocation when their cached copy
      expires.

   *  *Suspension and retirement.* If status is "suspended" or
      "retired", verifiers MUST treat all signatures and credentials
      from the agent as invalid.  A retired agent URI SHOULD NOT be
      reassigned to a different agent.

   Operators that need faster or auditable revocation MAY additionally
   record their AIDs and statements in a transparency service
   ([SCITT-ARCH]).  This document does not require it.

7.  Agent Statements

   An Agent Statement is a JWS [RFC7515] in compact serialization,
   signed with an Agent Key, that binds the agent to a specific version
   of a resource such as an Agent Card.  It allows protocol metadata to
   be served from any origin, mirrored, or included in registries
   without losing its link to the agent.

   The JWS Protected Header MUST contain:




Narvaneni & Ravi          Expires 23 April 2027                [Page 14]

Internet-Draft                  agent-uri                   October 2026


   *  typ: "agent-statement+jwt";

   *  alg: the algorithm of the signing key;

   *  kid: the agent URI with a fragment identifying the signing key,
      e.g., "agent://example.com/
      planner#kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k".

   The payload is a JWT Claims Set [RFC7519] with:

   iss:  REQUIRED.  The canonical agent URI.

   sub:  REQUIRED.  The URL of the resource the statement is about.

   resource_digest:  REQUIRED.  An object with members alg ("sha-256"),
      canon ("jcs" or "none"), and value (the base64url-encoded digest).
      With "jcs", the digest is computed over the resource canonicalized
      per [RFC8785]; with "none", over the exact bytes of the
      representation.

   iat:  REQUIRED.  Issue time.

   exp:  OPTIONAL.  Expiry time.  Statements about metadata that changes
      SHOULD expire.

   To verify a statement, a verifier: checks typ; resolves iss to an
   AID; checks that the kid agent URI equals iss; locates and checks the
   anchoring of the key; verifies the signature; checks iat and exp;
   fetches the resource at sub (or uses a copy); and compares its digest
   with resource_digest.

   Protocol metadata documents that support extension fields SHOULD
   include a reference back to the agent URI, so that a client starting
   from the metadata can find the identity.  How that reference is
   expressed is defined by each protocol (see Appendix A).

8.  Proving Identity in Requests

8.1.  HTTP Message Signatures Profile

   An agent proves its identity on an HTTP request by signing it with
   [RFC9421] as follows.  The profile is designed to be compatible with
   the architecture of [WEB-BOT-AUTH].

   The request MUST include a Signature-Agent header field whose value
   is a structured-field String [RFC9651] containing the canonical agent
   URI:




Narvaneni & Ravi          Expires 23 April 2027                [Page 15]

Internet-Draft                  agent-uri                   October 2026


   Signature-Agent: "agent://example.com/planner"

   The signature MUST:

   *  cover at least @method, @authority, @target-uri, and signature-
      agent, and content-digest [RFC9530] when the request has content;

   *  include the created and expires parameters, with expires no more
      than 300 seconds after created;

   *  include a keyid parameter whose value is the JWK Thumbprint
      [RFC7638] of the signing key; and

   *  include the parameter tag="agent-uri".

   A nonce parameter SHOULD be included where the verifier is expected
   to detect replay.

   Example:

   POST /v1/bookings HTTP/1.1
   Host: api.example.net
   Content-Type: application/json
   Content-Digest: sha-256=:...:
   Signature-Agent: "agent://example.com/planner"
   Signature-Input: sig1=("@method" "@authority" "@target-uri"
       "signature-agent" "content-digest");created=1760950000;
       expires=1760950060;
       keyid="kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k";
       tag="agent-uri"
   Signature: sig1=:...:

         Figure 4: A signed request (line breaks for display only)

   A verifier:

   1.  Parses Signature-Agent and canonicalizes the agent URI.

   2.  Selects the signature with tag="agent-uri".

   3.  Retrieves the AID (Section 5.5) and finds an anchored key whose
       thumbprint equals keyid, or, if an Agent-Instance field is
       present, validates the instance credential (Section 8.2).

   4.  Verifies the signature per [RFC9421] and checks that the current
       time is between created and expires, allowing for modest clock
       skew.




Narvaneni & Ravi          Expires 23 April 2027                [Page 16]

Internet-Draft                  agent-uri                   October 2026


   5.  Checks status (Section 6.3).

   On success, the verifier has established that the request was made by
   (an instance of) the agent.  On failure, the verifier MUST NOT treat
   the request as coming from the named agent; it MAY process it as an
   unauthenticated request.

8.2.  Agent Instances

   Agents frequently run as many short-lived instances, for example one
   per task.  Publishing a key for each instance in the AID does not
   scale, and keeping the agent's long-term private key in every
   instance is unsafe.

   Instead, the agent (through its controlling infrastructure) issues
   each instance an *Agent Instance Credential*: a JWT [RFC7519] signed
   with an Agent Key, with:

   *  protected header typ: "agent-instance+jwt" and kid as in
      Section 7;

   *  iss: the canonical agent URI;

   *  sub: an identifier for the instance, unique per agent and SHOULD
      be random (Section 13);

   *  cnf: a confirmation claim containing the instance's public key as
      a jwk;

   *  iat and exp.  The lifetime SHOULD NOT exceed one hour.

   The instance signs requests with its own key as in Section 8.1, with
   keyid set to the thumbprint of the instance key, and sends the
   credential in the Agent-Instance header field as a structured-field
   String.

   The verifier validates the credential against the agent's anchored
   keys, checks that iss equals the Signature-Agent value, and verifies
   the request signature using the key in cnf.

   This construction is intentionally close to the Workload Identity
   Token of [WIMSE-S2S]; see Appendix A.

9.  Authorization

   Identity is not authorization.  This section connects agent identity
   to OAuth 2.0 without defining new token formats.




Narvaneni & Ravi          Expires 23 April 2027                [Page 17]

Internet-Draft                  agent-uri                   October 2026


9.1.  The Agent as an OAuth Client

   An agent that obtains OAuth tokens SHOULD use a Client ID Metadata
   Document [OAUTH-CIMD] as its client identifier and link to it from
   its AID with rel="oauth-client-metadata".  The client metadata
   document SHOULD include the agent_uri client metadata parameter
   (Section 14.6) containing the canonical agent URI.

   An authorization server that sees agent_uri MAY verify it by
   retrieving the AID and checking that it links to the same client_id.
   When verified, the authorization server knows which agent the client
   is and MAY show the agent's identity and operator to the user at
   consent time.

9.2.  Delegation

   When an agent acts on behalf of a user or another agent, the
   delegation SHOULD be expressed with OAuth 2.0 Token Exchange
   [RFC8693], with the agent identified in the act claim by "sub" set to
   its canonical agent URI.  As required by [RFC8693], only the current
   actor is relevant to access-control decisions; nested actors are
   informational.

   Access tokens used by agents SHOULD be sender-constrained, for
   example with DPoP [RFC9449] using the agent's or instance's key, so
   that a stolen token cannot be used by a different agent.  Within a
   single trust domain, [TXN-TOKENS] can carry the agent identity and
   call context between services.

9.3.  Protected Resources

   Resource servers advertise their requirements using OAuth 2.0
   Protected Resource Metadata [RFC9728].  A resource server MAY require
   a valid agent signature (Section 8.1) in addition to an access token,
   and MAY apply policy based on the agent URI, its operator, or its
   DID.

10.  Discovery

   Dereferencing a known agent URI requires no discovery.  To let others
   find which agents a domain operates, a domain MAY list them in an API
   catalog [RFC9727] (a linkset [RFC9264]) at /.well-known/api-catalog,
   using the agent URI as the link context and agent-identity links to
   the AIDs:

Internet-Draft                  agent-uri                   October 2026


   {
     "linkset": [
       {
         "anchor": "agent://example.com/planner",
         "agent-identity": [
           { "href": "https://example.com/.well-known/agent/planner",
             "type": "application/agent-id+json" }
         ]
       }
     ]
   }

                 Figure 5: Listing agents in an API catalog

   Publishing a catalog is optional (Section 13).  Registries and search
   services that index agents SHOULD verify AIDs and statements
   themselves rather than asking clients to trust the index.

11.  Relationship to Other Protocols

   A2A:  An Agent Card describes how to communicate with an agent.  The
      AID links to it with rel="agent-card".  A2A clients can verify a
      card by checking the agent's statement about it.

   MCP:  MCP server metadata describes tools and how to reach them.  The
      AID links to it with rel="mcp-server-card".  MCP clients can use
      the agent URI and request signatures to identify the calling agent
      to MCP servers.

   OpenAPI:  The AID links to API descriptions with rel="service-desc"
      [RFC9727].

   Web Bot Auth:  [WEB-BOT-AUTH] lets automated clients sign requests
      and publish keys.  This document adds a named, operator-
      accountable identity and an optional DID anchor on top of the same
      signature mechanism.

   WIMSE:  WIMSE addresses workload identity inside and across trust
      domains.  Agent instance credentials (Section 8.2) address the
      same problem for agents; alignment is an open issue.

12.  Security Considerations









Narvaneni & Ravi          Expires 23 April 2027                [Page 19]

Internet-Draft                  agent-uri                   October 2026


12.1.  Trust Model

   For origin-anchored agents, the trust anchors are DNS and the Web
   PKI: anyone who can obtain a certificate for the agent URI's host and
   serve content there can impersonate the agent.  This is the same
   trust model as the web itself and is appropriate for most agents.
   DID-anchored agents can reduce this dependency, at the cost of
   trusting the DID method's security.

12.2.  Handle Reassignment

   If a domain lapses and is registered by someone else, the new holder
   can publish an AID for the same agent URIs.  Verifiers that record
   identities for audit or reputation SHOULD record the key thumbprint
   (and DID, when present) alongside the agent URI, and SHOULD treat a
   change of all keys for an agent as a significant event.

12.3.  Request-Destination Restrictions

   Signature-Agent values arrive in requests from untrusted parties, so
   any verifier can be made to fetch AIDs on attacker-chosen hosts.
   Verifiers MUST:

   *  refuse to fetch AID URLs whose host resolves to addresses in the
      IANA IPv4 and IPv6 Special-Purpose Address Registries that are not
      globally reachable, unless explicitly configured to allow them
      (e.g., for private deployments);

   *  apply the same check after every redirect and pin the resolved
      address for the duration of the fetch;

   *  enforce timeouts and the 64 KiB size limit; and

   *  rate-limit fetches per host and cache results, including failures.

12.4.  Replay

   Signatures cover the target authority and URI, which prevents replay
   against a different service.  The short created-expires window limits
   replay against the same service; verifiers for non-idempotent
   operations SHOULD require and track nonce values.










Narvaneni & Ravi          Expires 23 April 2027                [Page 20]

Internet-Draft                  agent-uri                   October 2026


12.5.  Key Compromise

   Compromise of an Agent Key lets the attacker act as the agent until
   the key is removed and caches expire.  Operators SHOULD keep Agent
   Keys in hardware or a key management service and use instance
   credentials (Section 8.2) so that long-term keys are never present in
   running agents.  Instance credentials SHOULD be short-lived, because
   they cannot be individually revoked.

12.6.  Cross-Origin Metadata

   Requiring statements for cross-origin links (Section 5.3) prevents a
   compromised or malicious third-party host from attaching metadata to
   an agent's identity.  A statement does not vouch for the _contents_
   of the resource beyond its integrity: an agent can make false claims
   in its own Agent Card, and verifiers must not treat identity as an
   endorsement.

12.7.  Confusable Names

   Agent URIs can be visually similar (e.g., examp1e.com).  User
   interfaces that display agent identities SHOULD display the operator
   name and the A-label form of the domain, and SHOULD warn when a DID-
   anchored agent's DID is new to the user.

13.  Privacy Considerations

   The considerations of [RFC6973] apply.

   *  *Linkability is the point, for agents.* Request signatures make an
      agent's traffic attributable and linkable across services.  That
      is intended for the agent; it must not extend to the people it
      acts for.  Agent URIs, instance identifiers, and Signature-Agent
      values MUST NOT encode user identifiers.  Instance sub values
      SHOULD be random and not reused across users.

   *  *Per-user agents.* Deployments that create one agent per end user
      (e.g., agent://example.com/u/alice) make that user's activity
      linkable across all services the agent visits.  Such deployments
      SHOULD use a shared agent identity and convey user context only
      through authorization tokens sent to parties entitled to it.

   *  *Enumeration.* API catalogs (Section 10) let anyone list a
      domain's agents.  Domains that do not want their agents to be
      enumerable should not publish them in a catalog; AIDs remain
      retrievable by those who already know the agent URI.





Narvaneni & Ravi          Expires 23 April 2027                [Page 21]

Internet-Draft                  agent-uri                   October 2026


   *  *Verifier fetches.* Fetching an AID reveals to the operator that a
      verifier has seen the agent.  Caching reduces this signal.

Appendix A.  Open Issues

   This appendix will be removed before publication.

   1.  *Web Bot Auth alignment.* [WEB-BOT-AUTH] uses Signature-Agent to
       point at a key directory URL.  Decide whether agent URIs become a
       permitted value of that field, whether the AID also serves as (or
       links to) an HTTP message signatures directory, or whether a
       distinct field is needed.

   2.  *WIMSE alignment.* Decide whether Agent Instance Credentials
       should be a profile of the WIMSE Workload Identity Token
       [WIMSE-S2S] with iss set to the agent URI, rather than a separate
       type.

   3.  *Back-references from protocol metadata.* Agree with the A2A and
       MCP projects on how an Agent Card or MCP server card names its
       agent URI, and who registers the agent-card and mcp-server-card
       link relations.

   4.  *Reserved root segment.* /.well-known/agent/_ is chosen to work
       on static hosting.  Alternatives (a separate well-known suffix
       for the root agent) should be evaluated.

   5.  *Name path depth and character set.* Lowercase LDH segments, at
       most 8, are chosen for unambiguous comparison.  Confirm this is
       sufficient for multi-tenant platforms.

   6.  *DNS-based verification.* Consider an alternative proof of
       control via a DNS TXT record (as for some handle systems), for
       operators that cannot serve well-known paths.

   7.  *Revocation latency.* Evaluate whether cache lifetimes alone are
       adequate, or whether a status list or transparency log should be
       RECOMMENDED.

   8.  *Port.* Confirm that non-default ports should be permitted in
       agent identities at all, given they complicate certificate and
       policy handling.

Appendix B.  Changes from draft-narvaneni-agent-uri-03

   This revision changes the scope of the document from "addressing and
   discovery" to "identity".

   Removed:

   *  agent+<protocol> transport-binding schemes and the Transport
      Bindings registry.

   *  Invocation semantics (GET/POST rules, fallback behaviour), query
      parameters in agent URIs, and conformance levels.

   *  The /.well-known/agents.json registry, replaced by the
      deterministic mapping of Section 4.3 and optional RFC 9727
      catalogs.

   *  The agent descriptor's capability fields (skills, transport,
      interactionModel, versioning, content negotiation).  Protocol
      metadata documents are linked instead.

   *  DID authorities in agent URIs, replaced by DID anchoring
      (Section 6.2).

   *  Cross-cutting conventions (tracing, idempotency, rate limits,
      health) and the Interaction Models registry.

   *  The monotonic scope narrowing rule, which conflicted with
      [RFC8693].

   Added:

   *  Strict URI syntax, normalization, and comparison rules.

   *  The Agent Identity Document and anchoring modes.

   *  Agent Statements, the HTTP Message Signatures profile, and Agent
      Instance Credentials.

   *  OAuth client and delegation bindings.

   *  Security and privacy considerations specific to agent identity.
